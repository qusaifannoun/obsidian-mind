- **Caught three independent duplicate-generation paths in a sequential-ID allocator before any of them could fire in production ([[tat-app-ws Backend]], 2026-07-28).** A new `userNumber` field (`001`, `002`, …) was allocated by scanning `users` for the current maximum — the obvious implementation, and wrong three separate ways, none of which shows up when you create one user at a time by hand. **(1)** The scan and the write aren't atomic, so concurrent signups read the same max and collide, with no unique index to reject it. **(2)** `UserSchema.add(BaseSchema)` merges the source schema's *`callQueue`*, not just its paths — so the soft-delete plugin's `deletedAt: null` filter silently applied to the scan, meaning soft-deleting the highest holder made their number invisible and the next signup reused it. **(3)** `userNumber` is a String, so `sort({userNumber: -1})` is lexicographic and `"999"` sorts above `"1000"` — past 999 users the scan would return `"999"` forever and assign `"1000"` to everyone thereafter, silently and permanently, long after the code looked proven. Replaced the scan with an atomic `$inc` against a counters document via the raw driver (bypassing the very middleware that caused #2), moved the uniqueness guarantee out of application code and into a **partial** unique index (partial because the 40 pre-existing users have no `userNumber` and would all collide as `null` under a plain `unique`), and made the field write-once with `immutable: true`. Separately caught that the field had been wired as a **client input on the public signup DTO** and forwarded into `create()` — which skips allocation entirely and leaves the counter un-advanced, and would have started returning raw `E11000`s to real users once the index went live. Wrote the backfill migration (createdAt order, raw driver so soft-deleted users keep their numbers reserved, `$max` counter seed so re-runs can't walk it backwards, duplicate repair), ran it, then **re-read the collection independently rather than trusting the migration's own output** — 40/40 numbered `001..040` in signup order, counter at 40, index spec confirmed. `ce3dd6cb`. **Honest caveat: the allocator itself has still never executed** — the backfill was a raw-driver bulk write that never touched `pre("save")`, so green migration output says nothing about whether the allocation path works; that remains the open verification.
