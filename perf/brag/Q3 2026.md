- **Root-caused why staff-management notification deep-links still pointed at the wrong host despite the env var, and redesigned the resolution ([[tat-app-ws Backend]], 2026-07-09).** After `STAFF_MANAGEMENT_URL` was set, staff notification links *still* resolved to the admin dashboard. Traced it to two compounding behaviors: the base URL was **baked into the stored setting at seed time**, and re-seeding **skips already-existing settings** — so the env var never took effect, and the send-time resolver was dead code (the stored URL was already absolute). Generalized the lesson into [[Patterns]] ("resolve env-dependent values at use time, never freeze them into a DB row") and [[Gotchas]]. Prevented broken deep-links reaching real staff. - **Caught a UI that was lying about compliance state, and killed the duplicated rule behind it ([[tat-app-ws Backend]] + [[tat-prereq]], 2026-07-12).** "The creation and expiry dates don't show once a TOR goes Active" reads like a rendering bug. It wasn't: **the TOR had never been activated, and the Active badge was lying.** The activation rule was implemented **twice** — six gates in the sync processor (the only thing that persists `status` and stamps `activatedAt`/`expiresAt`), but only **three** in the details endpoint behind the UI, which never checked required documents, aircraft qualifications, or assessments. Any TOR between the two bars renders as Active with blank dates *forever*, and the same weak rule fed `incomplete`, so the Pending-TORs worklist under-reported too. Resisted the pull toward the renderer and settled it from data instead: **46 `tor_sync_completed` audit rows (worker alive) + every TOR still persisted as `draft`** ⇒ the writer never agreed, so the reader was the liar — and the only two "active" TORs turned out to be June-6 seed fixtures with zero audit history, meaning **no TOR had ever legitimately activated**. Fixed by extracting `staff-tor-activation.util` so the reader and the writer share one rule, reusing the *same* service methods so they cannot drift again. Then found the reason Qusai believed the TOR *was* complete: the Assessment Report rendered as **one hardcoded "missing" row** — it says "missing" even when an assessment is approved (assessments aren't `StaffTorForm` records), and activation actually needs an approved assessment **per aircraft type**. His TOR had 3 aircraft types, 3 approved qualifications, and **1** assessment — two outstanding, with nothing on screen to say so. Expanded it into one row per aircraft type with real per-type status. **Third duplicated-rule bug of the week**, now generalized into a rule of its own ([[Patterns#One rule, one implementation — a duplicated rule doesn't drift, it lies (2026-07-12)]]). `57bb7a1c` / `ea43544`. Evidence: [[TOR Activation - Details Endpoint Lied About ACTIVE]], [[Gotchas]].
- **Found two notifications that had been dead for 9 days, by disproving my own documented rule ([[tat-app-ws Backend]], 2026-07-12).** Asked why Training Managers weren't notified when an assessment is submitted, I traced all eleven links of the chain and found **every one correct** — which was the tell. The vault's own gotcha said adding a notification takes **three** edits; a startup log Qusai pasted proved that wrong. `NotificationTemplate.code` is `@Prop({ enum: SystemActions })`, so a template code must *also* be a `SystemActions` member — `SIMV` and `ASNAR` never were, so Mongoose rejected the templates at boot, their settings were never created, and `sendNotification` no-opped on the missing settings. **Dead at three layers, with the only trace a `console.error` nobody reads.** So the *assessor-assigned* and *sit-in-moved* notifications had never once fired — the latter closing an open question from [[TAT-429 Sit-In Eligibility & Move Semantics]] that I'd flagged as "verify on deploy" and would otherwise have assumed fine. Fixed, verified both now seed, and **corrected the gotcha I'd written myself** (three edits → four). The TM notification, meanwhile, was never broken: the DB showed 3 assessments submitted and 1 notification row — the setting had been seeded on a restart *between* his tests. Also surfaced a permanent silent trap: the seeder **only re-syncs `parameters`**, never `destination` — so the seed file's `["TM","SA"]` will never reach the DB's `["TM"]`, and Super Admins can never receive it. Evidence: [[TAT-423 Assessment Report Rubric]], [[Gotchas]].
- **Root-caused and fixed a bug blocking all staff creation on staging ([[tat-app-ws Backend]], 2026-07-07).** A Mongoose enum `Prop` with `default: null` on `User.qualificationTrackingMode` failed validation on **every** new document, breaking `POST /auth/internal-user/signup` for all roles via both [[tat-prereq]] and the live backoffice. Used the "two independent frontends fail identically" signal to rule out the frontend and localize to the backend schema, traced the field's actual domain semantics against three expiry crons before choosing the fix, and identified this as the **3rd/4th instance of a recurring `enum + default: null` anti-pattern** across the schema — flagging it for a lint/schema-review rather than a one-off patch. Fixed and pushed same-day (`dc8f3a4f`). Evidence: [[Staff Creation Blocked - qualificationTrackingMode Enum Bug]], [[Gotchas]].
