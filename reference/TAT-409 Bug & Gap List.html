FIX FIRST

One field breaks three flows — tor.aircraftTypeIds is never populated

Nothing writes it (created [], no code path adds to it). That cascades into aircraft-qual creation (422 self-blocks), assignment eligibility (pickers render empty when an aircraft type is required), and qual validation (short-circuits to true). With the sibling missing “requested role” concept it also breaks Form 32 role-scoping and role-type eligibility. Resolve ownership (410 link-at-creation vs 422 derive-from-approved-quals) before anything else.

C1

tor.aircraftTypeIds is never populated (keystone)

TAT-410TAT-422TAT-424410 AC-02422 AC-01424 AC-10/12
tat-app-ws

Nothing writes the field — it's created [] in staff-tor.service.ts and no endpoint ever adds to it. Yet assertAircraftOnTor, the assignment-eligibility filter, and the refresher lookups all read it.

Fix
Decide the owner and populate it: link aircraft types at TOR creation (TAT-410 AC-02) or push the approved aircraftTypeId onto tor.aircraftTypeIds when a TAT-422 qualification is approved. Then backfill existing TORs. Blocks C3/C4 until resolved.

C3

TAT-422422 AC-01

Fix
Drop/relax the guard in create(), and add the approved aircraftTypeId to tor.aircraftTypeIds on approval (ties to C1).
