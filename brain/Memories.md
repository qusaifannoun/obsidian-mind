- **2026-08-12 (third piece)** — **The actual reason no TOR has ever activated: a stale BullMQ job id.** [[TOR Sync Never Re-Ran - Stale BullMQ Job Id]] — chased from Qusai asking why the GCAA TOR read `Active` with empty Creation and Expiry dates. The TOR details endpoint returns `torStatus: derivedStatus` (computed live) beside `activatedAt`/`expiresAt` read from the record, so the page showed Active with `—` dates while the TOR Matrix — persisted status — showed **0 active for all 18 staff across 40 TORs**. Same record, two screens, contradictory; the dates were the honest half. Root cause: `queue.add()` with a custom `jobId` that already exists in Redis **in any retained state, including completed**, creates nothing and **resolves as though it succeeded** (`addStandardJob-9.lua:89` → `handleDuplicatedJob` → `return jobId`). The TOR sync paired a fixed `tor-sync-${torId}` with `removeOnComplete: {age: 24h}` / `removeOnFail: {age: 7d}`, so **the key outlived the job**: one early sync ran while the TOR was incomplete, persisted `draft`, completed — and every approval afterwards enqueued a job Redis threw away, while `.then()` logged "Queued TOR sync job". Fix is two lines (`removeOnComplete/removeOnFail: true`, keeping the fixed id so pending syncs still dedupe), `tsc` exit 0, pushed as `9896faa3`. **This retro-explains the 2026-07-12 diagnosis** — "46 `tor_sync_completed` rows (worker alive) + every TOR still draft ⇒ the writer never agreed" — the writer was fine, nothing was ever asking it again. New [[Gotchas - Backend Services & Environment|gotcha]]: an idempotency key that outlives its operation turns "run once per event" into "run once, ever, per key". **Also this session: [[Final TOR Certificate - Form 020 Alignment & Export]]** — Qusai produced a real signed certificate PDF, and comparing it to the UI showed Course Rating/T1/T2 were collected **per aircraft** when Form 020 carries them **once per certificate** over a Limitations row; moved them to `TorCertificateData` (DSL stays per-row), and built the missing TAT Form 020 export mirroring the Form 031 pipeline — which is where `nonTrainingAuthorities` finally lands, correcting my earlier claim that nothing consumed it (missing output, not dead field). **Correction swept through four notes:** I had written up the certificate availability gate as blocking every TOR from activating. New [[Patterns - Method & Conventions|pattern]]: enumerate a flag's consumers before reasoning from its name, and treat a contradiction from running software as evidence — the UI was right and my read of the code was wrong **twice** today.
